# Dark Control updates and Windows releases

Dark Control uses the official Tauri v2 updater. Normal `main` builds and signed public releases are deliberately separate.

## What users get

- Settings contains an **Updates** section with the installed app version.
- Automatic update checks are enabled by default and can be disabled in Settings.
- A startup check stays silent when no update exists or when the network is unavailable.
- Manual **Check for updates** reports success or an error.
- When a newer release exists, Dark Control shows the release notes, current/new version and **Download and install**.
- Download progress is shown in the app.
- The updater verifies the Tauri signature before the installer is launched.
- Windows uses Tauri's `passive` install mode and requests relaunch after installation.

## CI artifacts from `main`

Every successful push to `main` builds and uploads the workflow artifact `Dark-Control-Windows-x64` containing:

- `dark-control.exe`
- the WiX/MSI installer
- the NSIS installer

These are development artifacts. They are retained by GitHub Actions for 30 days and are not the signed updater release channel.

## One-time updater signing setup

Tauri requires signed update bundles and does not allow signature verification to be disabled.

Generate a signing key pair locally:

```powershell
npm install
npm run tauri signer generate -- -w "$HOME/.tauri/dark-control.key"
```

Store the **private key** somewhere safe. Losing it means existing installations cannot trust future updates signed by a replacement key.

In GitHub repository **Settings → Secrets and variables → Actions**, create:

- Secret `TAURI_SIGNING_PRIVATE_KEY` — the full contents of the generated private key.
- Secret `TAURI_SIGNING_PUBLIC_KEY` — the public key printed by the Tauri signer command.
- Secret `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` — only when the generated key uses a password; otherwise leave it unset.

Never commit the private key.

## Updater endpoint and private repositories

The default release workflow embeds this endpoint into release builds:

```text
https://github.com/scarzxx/DarkProject-Soft/releases/latest/download/latest.json
```

That endpoint is suitable only when release assets are anonymously downloadable. If this repository remains private, installed applications cannot safely use private GitHub Releases without embedding a GitHub credential, which Dark Control intentionally does not do.

For a private source repository, publish updater files on a public HTTPS endpoint (for example a separate public releases repository) and set the GitHub Actions repository variable:

```text
TAURI_UPDATER_ENDPOINT=https://your-public-host.example/latest.json
```

The endpoint must expose the Tauri `latest.json` generated by the release workflow and the referenced signed installer assets.

## Publishing a release

Keep all application versions synchronized with one command:

```powershell
npm run release:version -- 0.4.1
npm install
```

Commit the version bump, then create and push the matching tag:

```powershell
git add .
git commit -m "release: v0.4.1"
git tag v0.4.1
git push origin main
git push origin v0.4.1
```

The `release` workflow verifies that the tag matches `package.json`, `src-tauri/tauri.conf.json`, and `src-tauri/Cargo.toml`. It then runs the frontend/Rust checks, creates updater-enabled MSI and NSIS bundles, signs them, generates `latest.json` and `.sig` files, uploads workflow artifacts, and publishes the GitHub Release.

If either signing key secret is missing, the workflow stops with an explicit setup error before attempting the release build.
